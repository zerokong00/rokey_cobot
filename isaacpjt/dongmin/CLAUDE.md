# 협동3 D-3 : 배관 점검 및 수리 로봇 (Isaac Sim)

배관 내부를 자율 주행하며 결함(금/크랙/누수/설계 누락)을 카메라로 탐지하고,
점검 데이터를 기록해 원인 규명의 객관적 근거를 만드는 로봇을 Isaac Sim에서 개발·검증한다.

## 목표 동작 흐름

```
현장 배치(배관 모델 설정) → 데이터 수집(센서값) → 결함 감지(금/크랙/누수)
   → 결함 존재? ─아니오→ 점검 완료
        └─예→ 원인 분석(영상 분석) → 수리 가능? ─예→ 수리 진행
                                        └─아니오→ 상세 보고(전문가 상담 필요) → 작업 종료
```

## 이번 주말 산출물

1. **크리티컬 포인트** — 아래 "크리티컬 포인트" 절
2. **환경 구성** — 배관 USD 씬 (직관/곡관/분기관, 조명, 결함 표현)
3. **로봇 형상 구성** — 주행부 + 센서 + 모듈형 매니퓰레이터

## 크리티컬 포인트

프로젝트를 실패시킬 수 있는 순서대로. 앞의 3개는 다른 모든 작업의 전제라 **가장 먼저** 검증한다.

### C1. 배관 내벽 충돌 처리 (최우선)

배관 내부는 **오목(concave)** 면이다. USD 메시의 기본 collision approximation은 convex hull이라
원통 안쪽이 **꽉 찬 덩어리로 근사**되어 로봇이 배관 안에 들어가지 못하거나 벽을 뚫는다.

- 정적 배관은 `triangle mesh` 또는 `SDF mesh` collision으로 지정할 것
- 곡관/분기관은 특히 위험 — 직관에서 되던 것이 곡관에서 깨지는 패턴
- **검증 방법**: 로봇을 배관에 넣고 낙하시켰을 때 바닥(내벽 하단)에 안착하는지, 관통·튕김이 없는지

### C2. 배관 내부 조명

배관 내부는 광원이 없어 카메라 영상이 전부 검게 나온다. 영상 기반 진단이 프로젝트의 핵심인데
**감지할 픽셀 자체가 없으면 뒤의 모든 인식 로직이 무의미**하다.

- 로봇 전방에 광원(SphereLight/SpotLight)을 부착해 카메라와 함께 이동시킬 것
- **검증 방법**: `/rgb` 프레임을 저장해 `mean` 밝기가 0에 가깝지 않은지 확인
- 참고: 밝기·노출은 결함 탐지 임계값에 직접 영향을 준다. 조명 확정 전에 임계값 튜닝하지 말 것

### C3. 결함을 시뮬레이션에 "만들어" 넣기

**없는 것은 감지할 수 없다.** 금·크랙은 형상이 아니라 표면 텍스처에 가까워서, 배관 메시만 놓으면
탐지 대상이 존재하지 않는다. 결함 표현 방식을 먼저 정해야 인식 알고리즘을 짤 수 있다.

선택지 (조합 가능):
- **텍스처/노멀맵** — 크랙 이미지를 내벽 머티리얼에 입힘. RGB 탐지용. 구현 쉬움
- **실제 형상 변형** — 메시에 홈/구멍. Depth 로도 잡히지만 제작 비용 큼
- **마커 프림** — 누수 지점을 작은 프림으로 표시. 정답(ground truth) 관리에 유리

각 결함에 **위치 정답값**을 함께 들고 있어야 탐지 성능을 정량 평가할 수 있다.

### C4. 배관 내경 대 로봇 크기

내경 대비 로봇 폭·높이 비율이 주행부 형식, 카메라 화각, 매니퓰레이터 작업 반경을 전부 구속한다.
**형상 설계보다 먼저 숫자를 고정**할 것. 곡관 곡률 반경에서 끼이지 않는지가 판정 기준.

### C5. 주행부 형식 선정

바퀴형 / 트랙형 / 나선(screw)형 / 다관절형. 곡관 통과성과 견인력이 상충한다.
매니퓰레이터를 얹으면 무게중심이 올라가 **배관 곡면 위에서 전복**하기 쉬우므로,
주행부 단독으로 곡관을 통과시킨 뒤에 상부 모듈을 올릴 것.

### C6. 누수 표현 수준

유체 시뮬레이션(파티클)은 비용이 매우 크고 실시간성을 해친다.
**초기에는 시각 효과 + 마커로 추상화**하고, 유체는 필요성이 입증된 뒤에 검토한다.

### C7. 점검 데이터의 위치-영상 동기화

프로젝트의 사업적 가치가 "법적 근거 제공"이므로, 영상만으로는 부족하고
**결함 위치(배관 진입점 기준 거리) + 타임스탬프 + 영상**이 한 레코드로 묶여야 한다.
시뮬에서는 로봇 오도메트리를 정답으로 쓸 수 있으니, 기록 포맷을 초반에 정하는 편이 싸다.

### C8. 판정 임계값과 fallback 금지

결함 판정 임계값은 **너무 조이면 아무것도 못 잡고, 느슨하면 오탐**이다.
반드시 실제 프레임을 저장해 픽셀 수·분포를 보고 데이터로 정할 것 (추측 금지).

그리고 **감지 실패 시 정답을 갖다 쓰는 fallback을 넣지 말 것.**
M0609 실습에서 실제로 겪은 함정이다 — 로봇이 정상 동작하는 것처럼 보이지만
실은 ROS 연동이 죽어 있어도 성공으로 찍혔다. 감지가 실패하면 **멈추고 드러내야** 한다.

### C9. PC 구성 (프로젝트 정의 표에서 비어 있는 항목)

M0609 실습에서 검증된 2-PC 구성을 그대로 쓰는 것을 권장한다:

| PC | 역할 | 비고 |
|---|---|---|
| PC A (GPU) | Isaac Sim, 로봇 주행, 카메라 발행 | GUI 필수 (아래 E2) |
| PC B (일반) | 영상 기반 결함 탐지·판단 노드 | ROS2 humble |

3대로 늘린다면 기록·리포트 생성을 분리. 단 **이미지 토픽 대역폭**이 병목이 될 수 있다
(실습에서 `/rgb` 24~32 Hz 실측).

## 실행 환경 (이 PC에서 실측 검증된 사실)

아래는 M0609 실습을 실제로 돌리며 확인한 내용이다. 추측이 아니라 재현된 동작이다.

### E1. Isaac Python(3.11) ↔ ROS Humble(3.10) 분리

`~/.bashrc`가 두 환경을 의도적으로 분리해 둔다.

```bash
ros_set    # source /opt/ros/humble/setup.bash        (Python 3.10)
isaac_ros  # LD_LIBRARY_PATH 에 Isaac 내장 humble lib 추가 (Python 3.11)
```

- Isaac Sim 5.1 = **Python 3.11**, ROS Humble rclpy = **3.10 빌드**
- 따라서 `isaac_python` 스크립트 안에서 **`import rclpy` 불가**
  (`_rclpy_pybind11.cpython-311-...so` 없음 에러)
- Isaac 쪽 ROS 통신은 **OmniGraph ROS2 브릿지 노드**로만 한다
  - 구독: `isaacsim.ros2.bridge.ROS2Subscriber` (범용, messagePackage/Name 지정)
  - 발행: `ROS2PublishImage`, `ROS2CameraHelper` 등
  - `OnPlaybackTick` → 노드 `execIn` 으로 연결해야 매 프레임 실행됨

### E2. headless 에서는 카메라 토픽이 발행되지 않는다

`--headless` 로 띄우면 `ros2 topic list` 에 `/rgb` 가 보여도 **실제 프레임이 오지 않는다**
(40초간 0프레임 실측). GUI 로 띄우면 24~32 Hz 로 정상 발행.
**카메라를 쓰는 검증은 반드시 GUI 로 할 것.**

### E3. 멀티 PC 통신 전제

```bash
export ROS_DOMAIN_ID=50            # 양쪽 PC 동일해야 함 (.bashrc 기본값은 143)
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/.ros/fastdds_whitelist.xml
```

`fastdds_whitelist.xml` 의 `interfaceWhiteList` 에 **두 PC의 실제 IP가 모두** 들어 있어야 한다.
현재 등록: `127.0.0.1`, `10.10.0.1~4`. 목록에 없는 PC 와는 토픽이 아예 보이지 않는다.

### E4. Python 출력 버퍼링

Isaac 스크립트를 리다이렉트하면 stdout 이 블록 버퍼링되어 **로그가 한참 밀린다**
(`stdbuf` 는 Python 에 효과 없음). 진행 상황을 실시간으로 보려면 `PYTHONUNBUFFERED=1`.

### E5. 물리 상태 전환 주의

`disable_rigid_body_physics()` 로 시뮬레이션이 꺼진 강체에 `set_linear_velocity()` 를 호출하면
PhysX 에러가 쏟아진다. **물리를 켠 뒤에** 속도를 세팅할 것.

## 재사용 가능한 참고 코드

`dongmin/M0609/` 는 이전 실습(두산 M0609 + 그리퍼 + RealSense)의 사본이다.
배관 로봇과 로봇은 다르지만 **패턴은 그대로 쓸 수 있다.**

| 파일 | 가져다 쓸 것 |
|---|---|
| `1_load_usd_standalone.py` | USD reference 로드 최소 골격 |
| `2_task_load_discovery_physics.py` | 프림 이름으로 경로 탐색, Drive 물리 설정 |
| `3_task_register_scene.py` | `BaseTask` 5단계 패턴 (LOAD→DISCOVER→PHYSICS→REGISTER→SCENE) |
| `4_pick_place.py` | RMPFlow 기반 매니퓰레이터 제어 (수리 모듈에 재사용) |
| `6_pick_place_color.py` | **OmniGraph ROS2 구독 + 상태 머신 + 색상 판정 연동** — 결함 탐지 연동의 원형 |
| `rmpflow/` | RMPFlow 컨트롤러·설정 파일 구성 방식 |

`6_pick_place_color.py` 의 구조를 배관 프로젝트에 그대로 대응시킬 수 있다:

```
SPAWN   → 결함 배치 / 로봇 배치
SETTLE  → 안정화
OBSERVE → 카메라를 대상에 정렬하고 ROS 판정 대기 (fallback 없이 대기)
PICK    → 판정 결과에 따른 동작 분기
FINISH  → 결과 기록
```

## Isaac Sim 문서 조회

Isaac Sim API·동작·설정을 확인할 때는 **기억이나 웹 검색보다 로컬 지식베이스를 먼저** 본다.
`/home/rokey/isaacsim_kb/` 에 5.1.0 공식 문서 전체(1,384개 문서 + Python API 색인)가 정리돼 있다.

```
1. /home/rokey/isaacsim_kb/INDEX.md  ← 라우팅 표. 항상 여기부터
2. 표가 가리키는 NOTES/0X-*.md 1개만 읽는다 (§N = 섹션 번호)
3. 부족하면 API_INDEX.md 를 grep / FILEMAP.md 에서 원문 경로를 찾아 그 파일만 읽는다
```

- `text/`(14MB)를 통째로 읽거나 광범위 grep 하지 말 것 — INDEX 가 그 역할을 대신한다
- **KB 에서 못 찾으면 일반 지식으로 메꾸지 말고 "없다"고 말한다.**
  Isaac Sim 은 4.5 확장 리네이밍·5.0 Core Experimental 도입으로 버전 간 API 차이가 크다
- 두산 M0609/RG2 사양, ROS 2 자체 문법, Isaac Lab 본체는 이 KB 범위 밖 (INDEX.md 에 목록 있음)

## 작업 규칙

- **Isaac Sim 관련은 KB 를 먼저 조회하고, 답에 근거 파일 경로를 남긴다** (위 절)
- **검증 없이 "된다"고 하지 말 것.** 로그·프레임 등 근거를 남긴다
- 임계값은 실제 데이터를 보고 정한다. 여러 조건을 한꺼번에 조이지 말 것
  (M0609 실습에서 ROI·마진·거리 조건 3개를 동시에 넣었다가 감지가 전부 죽었고,
   무엇이 원인인지 가리는 데 시간을 썼다)
- 감지·통신 실패는 **드러나게** 만든다. 조용히 우회하는 fallback 금지 (C8)
- 카메라 관련 검증은 GUI 로 (E2)
